# 精读的语音对话与知识点沉淀

日期: 2026-08-12

## 需求

1. 可以语音交互来进行精读对话
2. 根据意图自动记录知识点

范围限定在精读。精听（Live 语音课堂）的行为不变，本文只在一处动到共用代码，并明确
要求测试钉住精听行为。

## 现状

### 精读只有一个能用的入口，其余是死代码

`onExtractNote` 被穿过四层参数传下去，但**没有任何一行调用它**（`StudyView.swift:1704`
定义，零调用点）。连带失效的有：

- `NoteComposer` 整个面板 —— 说话和打字两条路都进不去
- `extracting` 加载指示 —— 参数传到 `TranscriptRow` 却从未出现在 body 里
- `StudyMode.showsNoteControls` —— 只有它自己的测试引用它

真正能用的只有：长按段落说话。

### 两套语音系统，各缺对方的一半

|  | 长按段落提问（quick-ask 抽取） | Live 语音课堂 |
|---|---|---|
| 交互 | 单次问答，无状态 | 实时双向对话 |
| 模型 | `qwen3.5-omni-plus`（HTTP 一次性） | `qwen3.5-omni-plus-realtime`（WebRTC） |
| 会记笔记 | 会 —— 按 intent 路由成词汇卡/问答卡 | **完全不会**，`transcript` 退出即蒸发 |
| 能追问 | **不能** | 能 |
| 老师出声 | **不会**（只返回 JSON） | 会 |

需求 1 只有 Live 满足，需求 2 只有 quick-ask 满足。**两个需求各被一半的系统满足，
而这两半不通。** 这是"设计得不好"的根源，不是某个交互细节。

### 架构层面的五个问题

**1. 你说的话去了哪里，你不知道。** `extractSpokenNote` 直接把音频扔给 HTTP，没有
任何转写反馈。模型听错时，你看到一张答非所问的卡，而无从判断是**听错了**还是**答错
了** —— 这两件事的应对完全不同（重说 vs 追问）。

更糟的是词汇卡路径：`StudyView.swift:398` 是 `request: nil`，走 vocabulary 分支时
**你的问题被完整丢弃**。问答卡至少保留 `question` 字段，词汇卡连这个都没有，回看时
不知道当初为什么问它。

**2. 不能追问，这是最伤的。** 每次长按都是全新的无状态 HTTP 调用，上一轮问答不进入
下一轮上下文。"那这里的 that 指什么"这种追问，模型不知道"这里"是什么。而精读的真实
节奏几乎总是追问式的 —— 一个疑问很少一句话解决。现在的机制强迫你把每个疑问重新表述
成自足的完整问题，这是在跟人思考的方式对抗。

**3. 只有你说话，老师不说话。** 返回 JSON 而非语音。这是语音**录入**，不是语音**对
话**。而 realtime 连接在进入精读时就已经建好（`startDiscussion()` 在 `.task` 里无条
件跑），只是精读把 `DiscussionBar` 藏了 —— 能对话的连接一直开着没被用。

**4. 问完必然产生一张卡，没有"不记"的选项。** 现在已经是全自动，而且是**强制的**：
vocabulary 分支存表达式，comprehension 分支存问答卡。随口确认一个已经懂的词也会留下
一张卡，卡片堆被"当时问了一下"的噪音填满。**缺的不是自动化，是判断力。**

值得注意：批量抽取的提示词早有这个精神 —— `ExtractionPrompt.rejectRules` 明确写着
"If this sentence genuinely holds nothing worth studying, return an empty array rather
than padding it"。**拒绝的能力已存在于代码里，只是没用在这条路径上。**

**5. intent 二选一且不可纠正。** `QuestionIntent` 只有 vocabulary / comprehension，
未知值一律落到 comprehension（`ExtractedExpression.swift:46`）。判定在服务端一次性
完成，返回后无法说"这个不用记"或"这个该记成词汇卡"。

### 体验层面的问题

**1. 松手之后屏幕上什么都没有。** `endAsking()` 在松手那刻就 `askingSentence = nil`
（`StudyView.swift:317`），波形立刻消失；`extractingSentenceId` 虽在异步任务里设上，
但**没有任何视图渲染它**（`ProgressView` 在整个文件里零次出现）。实际体感：

```
按住 → 波形动（我在听）
松手 → 波形消失，页面恢复原样，什么都没有
      ↓
   （几秒完全静默，不知道在处理还是失败了）
      ↓
   卡片突然出现
```

语音提问的等待恰恰最需要反馈 —— 刚说完话，最想确认的是"它收到了吗"。

**2. 0.35 秒的门槛不可见。** 按下到跨过阈值之间只有极淡的背景色
（`primary.opacity(0.06)`），震动只在跨过阈值时发生。按不够久 = 什么都没发生，而你
不知道为什么。

**3. 没有地方可以复习。** `learningExpressions` 和 `paragraphNotes` **只在 `StudyView`
里被读取** —— 没有笔记本、没有复习界面、没有跨集列表。知识点只存在于那一集那一段下
面，想回顾三天前学到的东西，得记起它在哪一集哪一段再滑过去。精读的产出就是知识点，
而知识点的价值在**重复看见**。

**4. 卡片默认折叠。** 折叠态只显示"N 张卡片"的摘要行，滑过一段有卡片的文字看不到内
容，想知道当初学了什么得逐个点开。

**5. 提示文案在说谎。** `StudyView.swift:1589` 的「点击蓝色词组展开精读卡片」—— 点击
高亮词已在 `9a9ccb8` 移除。按它说的做什么都不会发生。

**6. 错误处理粒度太粗。** 所有失败走同一个 `noteError` 弹窗（标题固定「记笔记失败」）：

| 实际情况 | 你看到的 | 应该怎样 |
|---|---|---|
| 没配 API key | 「记笔记失败：missingConfiguration」 | 引导去设置 |
| 网络断了 | 一个弹窗 | 提示重试 |
| 模型说这句没啥可记 | 「这句没有值得单独记的表达」当成**错误**弹出 | 这是正常结论 |
| 说话没被听到 | 静默无反应 | 至少说一声 |

第三行尤其值得说：`noUsableExpression` 是**合理的判断结果**，却被当成异常抛出并弹
窗。模型正确地说了"这里没什么值得记的"，而你收到一个失败提示。这正好和需求 2 相反
—— 你想要有判断力的记录，而现有代码把"判断不记"当成故障。

### 归纳

现状是「一次性语音查询」，要的是「带记忆的对话 + 有判断力的沉淀」。四个能力里，对话
记忆和拒绝记录从零开始，而语音输出和转写反馈**所需的连接与事件解析都已存在**，只是
没被精读消费。这是复用 realtime 而非新建的理由 —— 不是省事，是那条路上已经有一半。

体验问题集中在**反馈缺失**（松手后的静默、不可见的门槛、把正常结论当错误）和**产出
无归处**（没有复习入口、卡片默认藏起来）。前者让每次提问带着不确定感，后者让攒下来
的东西用不上。

## 决定

经讨论确定的五条：

| 议题 | 决定 |
|---|---|
| 对话机制 | 复用已连上的 realtime 连接，保持一问一答节奏 |
| 记录时机 | 自动判断，**可以不记** |
| 语音反馈 | 显示识别出的文字 |
| 对话位置 | 就在段落下方展开 |
| 播放行为 | 提问时暂停，答完**不自动继续** |

## 设计

### 一、核心思路

不新增语音栈。精读复用已经连上的 realtime 连接，但换一套节奏：

```
长按段落 → 说话 → 松手 → 老师语音回答 + 文字落在段落下方 → 可以接着追问
                                                    ↓
                                        对话告一段落 → 判断有无值得留的知识点
```

和精听的区别只在三件事：提问锚定在**你长按的那一段**（而非播放位置）、答完**不续
播**、对话轮次会**沉淀成卡片**。

### 二、四个组件

**1. `ReadingAskSession`（新）** —— 精读的一次对话。持有锚定的句子 id、这轮的
`[TutorTurn]`、状态（录音中/等回答/老师说话中/空闲）。需要它是因为 controller 的
`transcript` 是整集共享的，而精读要按「段落 + 这一轮」切分。

**2. `ClassroomScene`（改）** —— `inLive: Bool` → `enum { selfStudy, live, reading }`。
续播规则从「非 Live 就续播」（`ClassroomController.swift:260`）变成显式的每场景规
则。**这是唯一动到精听共用代码的地方，必须有测试钉住精听行为不变。**

**3. `KnowledgePointExtractor`（新，纯逻辑）** —— 输入一轮对话的文字轮次 + 锚定句
子，输出 `[KnowledgePoint]` 或空。**空是合法且常见的结果。** 不上传音频，消费已有转
写，所以少一次模型调用也少一次听错的机会。

**4. `ParagraphCards` 扩展** —— 知识点复用现有两种卡（词汇卡带高亮、问答卡无高亮），
不新增卡类型。

### 三、数据流

```
长按段落
  → controller.pressReadingAsk(sentenceId:)   // 锚定 + 暂停 + 刷新上下文到这一段
  → 你说话
  → 松手 → releaseReadingAsk()
  → input_audio_transcription.completed  → 你的话显示在段落下方
  → response.audio_transcript.done       → 老师的回答显示 + 语音播出
  → response.done → 场景 .reading → 不续播，等你追问
  → （可追问，回到第二步，同一 session 累积轮次）
  → 你收起对话 / 长按别的段落 / 离开精读
       → KnowledgePointExtractor 判断这轮有没有值得留的
       → 有则成卡，无则静默丢弃
```

`ClassroomController` 已在累积 `transcript: [TutorTurn]`，`RealtimeEventParser` 已解
析两种转写事件（`input_audio_transcription.completed` = 你说的话，
`response.audio_transcript.done` = 老师说的话）。**"显示我说的话"和"事后提炼知识点"
需要的原料已经存在**，只是退出时被丢掉。

### 四、关键取舍

**沉淀时机是「对话结束」而非「每轮结束」。** 一次追问链往往才构成一个完整知识点 ——
"这个 that 指什么" → "那为什么用被动" → 真正的知识点是两轮合起来的那件事。每轮记一张
会把一个知识点碎成三张。

**对话内容显示但不持久化，只有提炼出的知识点入库。** 理由：逐字对话记录会让段落下方
无限膨胀，而回看时你要的是结论，不是当时怎么问出来的。

**「不记」必须在提示词里被明确许可。** 提炼提示词沿用 `ExtractionPrompt.rejectRules`
同一套拒绝规则。同时 `noUsableExpression` 不再作为错误弹窗 —— 它是正常结论。

### 五、错误处理

| 情况 | 行为 |
|---|---|
| realtime 未连上 | 长按无反应 + 一次提示，不静默失败 |
| 说了但没听清（无转写） | 显示「没听清，再说一次」，不发请求 |
| 松手过快（无语音） | 静默取消，与现在一致 |
| 提炼判断为无可记 | 静默，不弹窗 |
| 提炼失败 | 对话内容已看过，静默丢弃不打扰 |
| 扬声器外放 | 精读答完不续播且是一问一答，不存在 Live 的自激问题 |

### 六、测试

纯逻辑层：场景续播规则（**含精听行为不变**）、提炼器在「无值得记」时返回空、追问轮次
的累积与锚定、转写事件到 UI 状态的映射。

需要真机验证（无法靠单测回答）：老师语音是否真的播出（有前科，见
`ptt-audio-unverified`）、外放下的实际体感。

## 风险

把精读和精听绑到同一个 `ClassroomController` 上，而那个类已有 448 行和相当微妙的
floor 仲裁逻辑（memory 里 `webrtc-server-vad-only`、`mic-gate-derives-from-floor`、
`quick-ask-mic-gating` 三条都是它的坑）。收益是不用维护第二套语音栈，代价是精读的
bug 可能碰到精听。缓解手段是场景枚举 + 钉住精听行为的测试。

外放是本方案**新增**的风险点（现状用 HTTP 一次性调用，不存在自激问题），需真机验证。

## 未纳入范围

以下问题已确认存在，但超出「语音对话 + 自动记录」两个需求，建议单独立项：

- **没有复习入口** —— 独立功能面，是知识点价值的关键（知识点的价值在重复看见）
- **卡片默认折叠** —— 与复习入口一并考虑更合适
- **提示文案在说谎**（`StudyView.swift:1589`）—— 一行文案，可随手修
- **死代码清理** —— `NoteComposer`、`onExtractNote`、`extracting`、`showsNoteControls`。
  若打字提问要保留，则 `NoteComposer` 需要重新接上而非删除；需先决定要不要打字入口
